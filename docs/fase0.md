Preparación del entorno
Antes de escribir cualquier código del proyecto se resolverán las dependencias necesarias. Se confirmará que OpenMPI esté instalado correctamente con mpicc y mpirun disponibles, y se instalará libssl-dev para tener acceso a openssl/des.h. Como primer paso de validación se hará una prueba mínima aislada que cifre y descifre un string corto usando la API de OpenSSL, para entender exactamente cómo se comportan las funciones antes de integrarlas. Este paso es crítico porque un error en la integración de DES contaminaría todos los programas posteriores. También se corregirá desde el inicio el bug del archivo base donde el loop de búsqueda usa int en lugar de long para iterar sobre las llaves, ya que el espacio de 2^56 desborda inmediatamente un entero de 32 bits.

Versión secuencial
El primer programa a implementar es la versión secuencial. Su propósito es doble para que sirva como prueba de concepto de que el cifrado, descifrado y verificación de la frase clave funcionan correctamente, y genera los tiempos de referencia contra los cuales se calculará el speedup de todas las versiones paralelas. La lógica es leer el texto desde el archivo .txt, cifrarlo con una llave conocida pasada como parámetro, y luego iterar sobre el espacio de llaves desde cero hasta encontrar la que al descifrar produce un texto que contiene la frase clave. Se medirá el tiempo de búsqueda con distintas longitudes de llave para observar cómo crece el tiempo de búsqueda. Las funciones encrypt, decrypt y tryKey que se implementen aquí serán reutilizadas en todos los programas siguientes, por lo que se aislarán en un archivo utilitario compartido desde el principio.

Enfoque Naive con MPI
El segundo programa implementa el enfoque naive adaptado directamente desde bruteforce.c. El espacio de llaves [0, 2^56) se divide en N segmentos contiguos e iguales, uno por proceso, donde el proceso con rango i trabaja sobre el rango [i × (2^56/N), (i+1) × (2^56/N)) e itera incrementalmente. El texto cifrado se distribuye a todos los procesos al inicio mediante MPI_Bcast. El mecanismo de comunicación usa MPI_Irecv no bloqueante al inicio de cada proceso para que esté escuchando si algún otro ya encontró la llave, y dentro del ciclo de búsqueda se verifica periódicamente con la variable found si llegó esa señal. Cuando un proceso encuentra la llave, notifica a todos los demás con MPI_Send y termina. A diferencia del archivo base, se manejará más limpiamente el MPI_Irecv pendiente de los procesos que no encontraron la llave, para evitar problemas de sincronización al llamar a MPI_Finalize.
Con este enfoque se realizarán las tres pruebas específicas del enunciado usando 4 procesos, siendo la llave 123456L que es pequeña y se encuentra rápidamente en el segmento del proceso 0, la llave (2^56)/4 que cae al final del segmento del proceso 0 haciendo que ningún otro proceso contribuya y el speedup sea aproximadamente 1, y la llave (2^56)/4 + 1 que es la primera del segmento del proceso 1 y se encuentra en el primer intento de ese proceso produciendo un speedup artificialmente enorme. Estas pruebas sirven para evidenciar el fenómeno central del proyecto: el speedup del naive depende completamente de la posición de la llave en el espacio de búsqueda, haciéndolo inconsistente e impredecible.

Alternativa 1: Distribución Cíclica
El primer enfoque alternativo ataca directamente el problema de inconsistencia del naive. En lugar de asignar bloques contiguos, cada proceso toma llaves intercaladas a lo largo de todo el espacio: el proceso 0 trabaja con las llaves 0, N, 2N, 3N, ..., el proceso 1 con 1, N+1, 2N+1, ..., y así sucesivamente. De esta forma, la llave tiene la misma probabilidad de ser encontrada pronto por cualquier proceso independientemente de su valor absoluto, ya que todos cubren el espacio de búsqueda de forma distribuida desde el inicio. El mecanismo de comunicación MPI es idéntico al naive, únicamente cambia la forma en que cada proceso genera su secuencia de llaves a probar, lo que hace esta alternativa relativamente directa de implementar una vez que el naive está funcionando.

Alternativa 2: Distribución Aleatoria con LCG
El segundo enfoque alternativo lleva la idea de consistencia más lejos. Cada proceso recorre el espacio de llaves en un orden pseudoaleatorio usando un generador congruencial lineal con una semilla distinta por proceso. Con parámetros correctamente elegidos, el LCG tiene un período de exactamente 2^56, garantizando que se prueben todas las llaves sin repetición. Esto elimina casi por completo la correlación entre el valor de la llave y el tiempo que tarda en encontrarse, produciendo el comportamiento paralelo más consistente de los tres enfoques. La mayor complejidad aquí está en verificar que los parámetros del LCG satisfacen el teorema de Hull-Dobell para garantizar período completo, lo cual se documentará en el informe.

Mediciones y análisis de speedup
Una vez implementados los cuatro programas se realizarán mediciones sistemáticas con tres clases de llaves representando distintos escenarios de dificultad. La llave fácil tiene valor (2^56)/2 + 1, la llave medianamente difícil tiene valor (2^56)/2 + (2^56)/8, y la llave difícil tiene valor (2^56)/7 + (2^56)/13 redondeada al entero superior. Para cada combinación de enfoque y clase de llave se calculará el speedup como T_secuencial / T_paralelo y la eficiencia como speedup / num_procesos. Lo esperado es que el naive muestre speedups muy variables entre las tres clases, la distribución cíclica muestre valores más estables, y la distribución aleatoria muestre el comportamiento más consistente de todos. Todos los resultados quedarán registrados con capturas de evidencia en el Anexo 2 del informe.

Extras
Se intentarán los tres extras disponibles con la disposición de descartarlos si no resultan viables en el tiempo disponible. Para el extra del cluster MPI entre múltiples máquinas, que vale hasta un 20% adicional, se comenzará probando con Docker en una sola máquina levantando múltiples contenedores en una red virtual para verificar que la configuración de MPI funciona correctamente entre ellos. Si esa prueba es exitosa y el Wicho nos confirma que Docker no cuenta como virtualización en el sentido que excluye el enunciado, se queda. De lo contrario, o en paralelo, se intentará con las laptops físicas de los integrantes del equipo conectadas en la misma red local, que es el escenario explícitamente descrito en el enunciado. Para el extra de los tres o más enfoques alternativos al naive, que vale hasta un 5% adicional, se evaluará una vez que los dos enfoques principales estén funcionando si hay tiempo y energía para proponer e implementar un tercero, posiblemente una búsqueda bidireccional dentro de cada segmento o una distribución por bloques no uniformes. El extra de OpenMP combinado con MPI, que vale hasta un 10% adicional, se intentará solo si da tiempo ya que añade una capa significativa de complejidad de sincronización.
